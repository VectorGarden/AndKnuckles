# Asset pipeline

Everything the scenes draw is decoded from the disassembly's own data rather than
screenshotted, then pasted into `index.html` as base64 PNGs. This is
that pipeline. Nothing here ships in the page — it exists so the artwork can be
rebuilt, checked, or changed.

```bash
go -C tools/go run .                # everything, in order
go -C tools/go run . --check        # verify without changing anything
```

It is Go, on the standard library alone: no dependencies to install. `npm run build` and
`npm run check` run the same two.

`--check` restores whatever it found and exits non-zero if the pipeline and the
committed `index.html` disagree, so it is safe to run against a dirty tree. It runs
on every pull request via [`.github/workflows/assets.yml`](../.github/workflows/assets.yml),
so the page and `tools/` cannot drift apart without the check failing.

The steps underneath, if you want to run one on its own (an output directory is optional,
and defaults to `tools/out`):

```bash
go -C tools/go run . sk        # rom/ -> out/  (17 PNGs + intro-meta.json)
go -C tools/go run . s3        # rom/ -> out/  (background + banner sheet)
go -C tools/go run . aiz       # rom/ -> out/  (the AIZ intro's layers and timeline)
go -C tools/go run . font      # font/ -> out/ (sprite font atlas + glyph table)
go -C tools/go run . cardfont  # rom/ -> out/  (the S3&K title card)
go -C tools/go run . s1        # rom/ -> out/  (Sonic 1: title, GHZ, credits, card, logo)
go -C tools/go run . s2        # rom/ -> out/  (Sonic 2: title, credit font, card, EHZ)
go -C tools/go run . music     # rom/ -> out/  (each scene's music log and DAC samples)
go -C tools/go run . embed     # out/  -> src/generated/assets.js
go -C tools/go run . page      # src/  -> index.html
```

Reach for the full run by default. `embed` only touches scenes whose files are in
`out/`, which is the sane behaviour for a partial run but means running two of the
three builds and then embedding would quietly ship a page assembled from a stale
`out/`. The full run wipes `out/` first and runs the lot.

The code is in [`go/`](go/):

- **`lib/`** — the decoder set, PNG, sprite mappings and shading, and what keeps the output
  exact:
  - the deflate;
  - a JSON writer that matches `JSON.stringify` (the page's JavaScript reads the tables);
  - a reader for the data literals in `tools/font`;
  - `Math.hypot`, `atan2`, `sin`, `cos` and `round` as V8 computes them.
- **`fonts/`** — reads `tools/font/s1-logo.mjs`, evaluating its shape calls.
- **`sound/`** — the music: an assembler for smps2asm songs, a port of the S&K sound
  driver, the DAC samples' DPCM, and the log the page plays.
- **`steps/<name>/`** — one build step each, described below. Each step's test builds it
  into a fresh directory and requires every PNG it writes to be the one the committed page
  carries, byte for byte, so a step that drifts from the page fails its own test by name.

```bash
go -C tools/go test ./...
```

## What sk does

1. **Kosinski** and **moduled Kosinski** for the tile art — background, the
   standing Sonic/Knuckles blob, the landing frames, the Death Egg, the mountain,
   falling Sonic, and the hand animation art.
2. **Replays the runtime DMAs.** The tiles for Knuckles' face and fists are
   placeholders in the ROM blob; `Obj_SKTitle_HandAnim` overwrites them at
   runtime. Skip that and you get leftover garbage across his chest.
3. **Enigma** for the plane tilemaps — the background and the four
   `SK SonicKnux Frame` poses.
4. **Composes** the layers, crops each to what it actually covers, and writes
   indexed PNGs plus `intro-meta.json` (offsets, anchors, and the hand channels'
   frame tables).

Sprite mappings are read straight from the disassembly's `.asm` by `go/lib/sprite.go`,
which both builds share.

The hand overlays are generated by patching the standing art one channel-state at
a time, re-rendering Plane A, and keeping only the pixels that changed — which is
why all eight together come to about 3 KB.

## What s3 does

The S3 screen is two planes rather than a layer stack: **Enigma** for both, plane B
the sky and scenery, plane A Sonic and the foreground drawn over it with index 0
transparent, over **Kosinski** tile art. The banner is a sprite in the original and
part of neither plane — which is exactly the gap the generated text drops into.
It writes them flattened (`s3-back.png`, the still) and apart (`s3-plane-a/b.png`),
because Tails' plane flies between them.

For the opening it renders the thirteen `TitleSonic_Frames` pictures plus the
`Pal_Title` fade steps and the white flash as `s3-i00`–`s3-i19`, and the title
objects' sprites from `S3 Sonic Sprites.nem` (**Nemesis**) through their mapping
files: the finger and wink frames as patches over plane A, Tails' six frames in both
directions. Durations and animation tables go to `s3-intro-meta.json`. It refuses to
build if Tails ever uses line 3's colours 13–14, which the banner's water cycle
rewrites.

It also writes `s3-banner-tiles.png`, which is **not embedded**. That is
`ArtNem_Title_S3Banner` — Nemesis, 214 tiles — dumped as a grid so the real **3**
can be read off it. The digits were drawn against that, which is where their flat
terminals and 45° chamfers come from.

Neither background carries a `tRNS` chunk. They are opaque by definition and will
happily use their lowest palette slot as a real colour; reserving index 0 for
transparency punches holes in them. It did exactly that to Sonic's pupils once.

## What aiz does

The Angel Island intro is a cutscene in the level engine, so this build is mostly a
simulation. It decodes AIZ1's level the way the intro loads it — Primary tiles at 0 and
the intro's Secondary tiles straight after (tile `$BE`), Secondary blocks appended to
Primary's, the chunk table, the layout, and the S3-format collision with the height
maps — then steps every object routine frame by frame and records each frame's camera,
background scroll value, palette and sprite list. See the root README for what the
cutscene is and how the transcription was checked.

It writes palette-index layers rather than colour ones, grey level `g*4` for index `g`:
plane A split by tile priority (`aiz-fg.png`, `aiz-fg-hi.png`), plane B (`aiz-bg.png`),
and every sprite frame that appears, packed into `aiz-sprites.png`. Sprites with DPLCs
(Sonic, Super Sonic, Knuckles) are assembled from the tiles each frame loads.
`aiz-meta.json` is the timeline, run-length coded where it can be. `aiz-still.png` is
the last frame composited with its palette, for still mode.

Two guards: it throws if any emerald is still on the ground at the end (the simulation
has drifted), and if any tile the AIZ1 tile animation rewrites from F755 is on screen
after it (none are, so no animated tiles are needed).

Mapping and DPLC files with several tables in one (`Map - Sonic.asm` has `Map_Sonic`
and `Map_SuperSonic`) are read by `go/lib/sprite.go`, which all three scene builds share.

## What s1 does

The Sonic 1 title screen and credits face, from s1disasm. It decodes the GHZ background
(Enigma blocks, Kosinski 256×256 chunks, the S1 layout format, `Nem_GHZ_1st`) as the 512px
plane `GM_Title` first fills, the emblem (`Eni_Title`, whose words already carry its `$200`
tile base), TitleSonic's eight frames and the TM, all as palette-index layers; computes the
fade and water-cycle palettes; and writes `s1-meta.json` with the timeline's constants. It
asserts that the page's timeline ends before the hills strip's column redraws would make
the plane differ from that first fill.

S1 mappings are macro calls (`spriteHeader` / `spritePiece x, y, w, h, tile, xflip, yflip,
pal, pri`) rather than bytes; `go/lib/sprite.go` reads them into the same piece layout as the
S3K ones, so one renderer draws both.

The credits face comes straight off `Map_Cred`, whose pieces are commented with their
characters, and the missing glyphs are derived and bevelled (`cred-atlas.png`,
`cred-table.json`). The Sonic 1 title card is read off `Map_Card` the same way, with the
unused K, U and full stop taken from the art by tile, its missing glyphs derived and
re-shadowed, and ZONE, ACT 1-3 and the oval rendered as parts (`s1card-*`); its table also
carries the card's positions and speeds from `Card_ItemData` / `Card_ConData`. Last, the GHZ
scene: GHZ1's foreground at the start camera (0, `$300`), split by priority, over both halves
of the GHZ art; Sonic's standing frame; and the level palette's fade and water cycle
(`ghz-*`).

For the S1 logo style it also writes the emblem with its lettering cleared
(`s1-emblem-clean.png`: the ribbon's flag pattern repainted row by row, the ornaments kept by
their mirror symmetry), and `s1-logo.json`: the lifted S O N I C and T H E D G O masks, the
drawn glyphs from `font/s1-logo.mjs`, the gradient read down the real I, and the face's
placement and shadow constants.

## What s2 does

The Sonic 2 title screen and credit font, from s2disasm. It loads VRAM in `TitleScreen`'s
order (the credit font first, then the title art over and around it) and renders from it:
plane B, the two background maps side by side across the 512px plane; plane A, the emblem
with the copyright line written over it; and `Obj0E`'s mapping frames, each split into its
high- and low-priority pieces.

Then it runs the screen. `Obj0E`'s routines and `ObjC9`'s palette fades are transcribed from
`s2.asm`, and they run in object-slot order the way `RunObjects` runs them, with sprites
queued by priority the way `BuildSprites` lists them. It covers the fade-in, the loop and
`SwScrl_Title`'s scroll. Every frame is written to `s2-meta.json`, and the still is rendered
from the same table. It asserts that the flash lands on `Obj0E`'s frame 288, and that the
palette has settled by the time the text arrives.

The credit font comes off `creditText`'s character map: each letter is an upper-case code
and a lower-case one, two tiles. The glyphs the game never spells are drawn
(`s2cred-atlas.png`, `s2cred-table.json`).

**The title card.** The letters come from the title-card font at the offsets its character map
gives, plus E N O Z from the card's own art. The parts (ZONE, the act numbers, SONIC THE
HEDGEHOG, the stripes, and the three fills) come from `MapUnc_TitleCards`, which is excerpted
unchanged into `rom/` because it sits inline in `s2.asm`.

`Obj34` is run in slot order, and every frame's state goes into `s2card-table.json`. That state
covers the fill rows and columns, each sprite's x, and where the level has been drawn over the
blue. The hold lasts until the zone's pattern-load requests would have finished, at 6 tiles a
frame, using the tile counts from the Nemesis headers.

**Emerald Hill.** The zone's Kosinski art, blocks, chunks and act 1 layout are drawn at the
start camera (0, `$22F`). The foreground is split by priority, and the background is drawn the
way `DrawInitialBG` draws it. `APM_EHZ` is patched into the block table, and the flower cells it
brings on screen are kept as overlays per `Animated_EHZ` frame. Sonic, Tails, his tails and the
rings are rendered from their DPLC-loaded sheets and ring art, along with the palettes the card
and the level go through (`ehz-*`).

**The logo.** It writes the emblem with SONIC and THE HEDGEHOG cleared (`s2-emblem-clean.png`):
the arched ribbon is refilled from a parabola that it checks against every pure-ribbon column,
and the curled ends are kept by their mirror symmetry. It clears the banner-top sprite the same
way (`s2-spr-top-clean.png`). Then it writes `s2-logo.json` with the face's placement, the
gradient down S2's I, and T H E D G O lifted from S2's small lettering. The chrome shapes are
`font/s1-logo.mjs`'s: its `SONIC` is what the S1 build lifts, which that build checks, and the
S2 build checks S2's letters against the same shapes.

## What font does

The one build here that is **not** a decode. The ROM has no title font at all:
`Map - S3 ANDKnuckles.asm` is six sprite pieces making a flat 168&times;24 bitmap of
the phrase, so only **& C E K L N S U** trace to real game pixels. The other twenty
letters were reconstructed by the ripper, and the digits and punctuation were drawn
for this project.

So `font/base/` is **source data, not something regenerable** — the ripped sheet,
28 glyphs, credited in the root README. The build is additive on top of it:

| stage | source | glyphs |
|---|---|---|
| ripped sheet | `font/base/` | 28 |
| + digits | `font/masks.mjs` | 38 |
| + keyboard punctuation | `font/punct.mjs` | 68 |

Both generated sets are authored as `#` masks at plain size and run through the
same shading rule in `go/lib/shade.go`, so they cannot drift from the sheet's own
weight — gold body, ember on the right of every horizontal run and the bottom of
every vertical one, flare a pixel in from the left, and an L-shaped glint at the
top-left corner. Fed the real **I**'s outline that rule reproduces the real **I**
pixel for pixel, which is what made it safe to point at shapes the game never drew.

That holds best for uprights. Against the sheet's own glyphs the rule matches M 84%,
A 75%, X 73%, W 68% and V 66% — the artist hand-placed the rim light on diagonals. So the
build redraws **W** (44px, now 36) and **X** (16px, now 22) but leaves **V** alone, since a
redrawn diagonal does not sit quite like its neighbours.

W shrinks, so it goes back in its own slot. X grows, so it cannot: at 22 plain it would abut
Y and at 26 outline it would overlap it. It is appended below the punctuation instead and its
old slot cleared, which is what the size guard in `redraw()` is there to catch.

`'0'` is not drawn at all: it is the real **O**'s own mask, so the two cannot
disagree. `'9'` is `'6'` rotated 180&deg; in `masks.mjs` for the same reason.

The build asserts what the layout depends on: every glyph's height matches its
style's row height, and no glyph overflows its row band once its `yOffset` is
applied. Both are how a period ends up on the baseline and a quote at cap height
without padding the bitmap.

## What cardfont does

Decodes the title-card lettering. It loads the title card's art the way `Obj_TitleCard`
queues it — Red ACT at tile `$500`, the shared letters at `$510`, the act number at `$53D`,
each zone's own letters at `$54D`, later loads winning — renders each zone-name frame of
`Map - Title Card.asm`, and splits the names back into letters using the pieces' positions
and widths learned from one-letter-per-piece words. It throws if a letter differs between
two names, or if a word's letters do not exactly fill its pieces.

J, Q, W and X are derived at the end of the file, and the anti-aliasing rule used for the
drawn strokes is checked against the real V on every build. Writes `card-atlas.png`, in the
title card's own colours (Sonic's palette line, which the card is drawn in), and
`card-table.json`, the same shape as the main font's table plus two extras: `parts`, the
offsets of the rest of the card (the banner in its three versions — `card-banner-s3.png`,
`-s3k`, `-sk`, one per game, by what loads at `$510` — and ZONE and both act numbers,
`card-zone.png`, `card-act1.png`, `card-act2.png`), and `card`, the
elements' start and rest positions, speeds, hold and exit order from `ObjArray_TtlCard`.

## What music does

Writes `music.json`: for each scene with music, the log of what its game's sound driver sent
the YM2612 and PSG on every V-int, and the DAC samples it queued. The root README's
*The music* has the whole of it; the parts that live here:

- **Assembling the song.** `sound/asm.go` takes the smps2asm macros the way
  `_smps2asm_inc.asm` expands them for S&K (`SonicDriverVer` 4, songs from source driver 3),
  in two passes so labels can be used before they are defined. Sonic 3's build
  (`SonicDriverVer` 3) expands every macro these songs use the same way. Pointers are `z80_ptr`s
  through the $8000 bank window. Each voice in a song is preceded by a comment with the 25
  bytes it assembles to, and the test requires the macros to land on them. The two songs
  were converted by different smps2asm versions — S&K's takes the TL carrier bits as written,
  S3's derives them from the algorithm — so between them both paths are checked. Songs that
  test build options with `if`/`else`/`endif` get the stock build's answer
  (`FixMusicAndSFXDataBugs` = 0), so their data bugs stay in. The universal voice bank at
  the end of the driver source is assembled the same way, and its comments checked too.
- **Running it.** `sound/s3k.go` is the music half of the driver, for both games: `zStopAllSound`,
  `zBGMLoad`, then one `zUpdateMusic` per V-int until every track has stopped. Its frequency
  and envelope tables are read out of the driver source, frequencies through AS's integer
  clock arithmetic (`FM_Sample_Rate` is 7670453 / 144, an integer).
- **The samples.** `sound/dac.go` reads `DAC_Setup` out of `sonic3k.macros.asm` for each
  sample a song queues, converts its WAV with the build's own `convert_dpcm_file` logic (the
  closest delta, the first of a tie, two nibbles a byte, high first) and works out its djnz
  count with `dpcmLoopCounter`.

The step's test requires `music.json` to be the `MUSIC` the committed page carries.

## What page does

Inlines `src/style.css`, `src/generated/assets.js`, `src/sound.js` and `src/app.js` into
`src/index.html` and writes `index.html`. The deployed site stays a single
self-contained file; the split is only so the sources can be read and edited.

It refuses to run if `src/app.js` or `src/sound.js` contains base64 — generated data belongs in
`src/generated/` — and checks the assembled page has a closing `</html>`, which is
one of the two guards the Pages deploy applies. Better to fail here than there.

## What embed preserves

Only the artwork and the geometry that comes with it are replaced. Every timing
value — the camera phases, the shake, the reveal, and the hand channels' `phase`
and `delay`; on S3 the logo `hold`, the loop's `idle` and Tails' `x0` — is read back
out of `index.html` and kept. AIZ has no hand-tuned numbers, so its entry is
regenerated whole; only its text position is kept. Regenerating the art
cannot silently undo tuning that was arrived at by eye.

## What keeps the output exact

The page's artwork is checked byte for byte, so three things are pinned down rather than left to
the toolchain:

- **Compression.** [`go/lib/deflate.go`](go/lib/deflate.go) is stock zlib's level-9 deflate,
  transcribed, and its test checks it against the system zlib through Python on every PNG the
  page carries. The PNGs do not depend on whichever zlib a toolchain happens to bundle: Node's,
  which built them before, is Chromium's patched one, which nothing else reproduces.
- **Floating point.** A few font shapes are tested point by point against a distance or an
  angle, and an edge can turn on the last bit:
  - The maths is V8's (fdlibm), which first drew them.
  - Go may fuse `a*b + c` into a single multiply-add, where V8 on x86 never does. So every
    product that feeds a sum is rounded explicitly with `float64(...)`.
  - The maths test holds the results to V8's bit for bit on x86-64. On arm64, V8 is itself
    compiled with fused multiply-adds and can differ by one unit in the last place, so the
    test allows that there.
- **The semantics the steps were written with.** These are reproduced explicitly:
  - reads past the end of an array give 0, and stores past it are dropped;
  - `Math.round` rounds halves up;
  - objects iterate in insertion order, integer keys first;
  - sorts are stable;
  - a loop over a growing list of objects sees the new ones.

The font designs in [`font/`](font/) stay in the JavaScript syntax they were drawn in: data and a
few shape calls, which the steps read from that source.

## rom/

Compressed source data from the Sonic Retro disassemblies, unmodified: [skdisasm][disasm],
and [s1disasm](https://github.com/sonicretro/s1disasm) and
[s2disasm](https://github.com/sonicretro/s2disasm) for the `S1_` and `S2_` files.
It is Sega's, like the rest of the artwork this project renders — see the credits
in the root README. The sound files are sources rather than compressed data: a song's
smps2asm text (`SK_Snd_Title.asm`, `S3_Snd_Title.asm`, `S3K_Snd_AIZ1.asm`), the Z80 sound driver (`S3K_Snd_Driver.asm`, read for
its tables and its universal voice bank), `sonic3k.macros.asm` (`S3K_macros.asm`, for `DAC_Setup`), and the DAC WAVs
with the driver's `deltas.bin`. The page already embeds the decoded results; these are the
inputs they came from, kept here so the build runs without a network fetch.

[`go/lib/`](go/lib/) holds the decoders: Kosinski and moduled Kosinski, Enigma, Nemesis,
and an indexed-PNG reader/writer. They were written against
[flamewing/mdcomp][mdcomp]; the traps worth knowing about are recorded in the root
README under *Compression formats implemented*.

[disasm]: https://github.com/sonicretro/skdisasm
[mdcomp]: https://github.com/flamewing/mdcomp
